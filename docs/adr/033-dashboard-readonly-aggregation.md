# ADR-033: 대시보드는 엔티티 없는 읽기 전용 도메인으로 두고, 집계는 조회 전용 쿼리 조인으로 처리한다

- 상태: Accepted
- 날짜: 2026-10-24

## 컨텍스트
본사 홈은 지점 발주, 창고 발주, 입고, 출고, 재고, 창고를 가로지르는 집계(조치 대기 건수, 진행중/완료 입출고, 재고 총량, 상태 분포, 창고별 비교, 월별 추이)를 한 화면에 보여준다. 이 집계는 어느 한 도메인에 속하지 않는다. 기존 도메인 중 하나에 넣으면 그 도메인이 나머지 도메인의 테이블을 읽는 구조가 되고, 서비스에서 각 도메인 UseCase를 호출해 조합하면 창고·SKU 단위로 호출이 반복되어 [ADR-007](007-inventory-query-jpql-cross-domain-join.md)이 피하려던 N+1이 생긴다.

## 결정
- `dashboard` 패키지를 새 도메인으로 두되 **엔티티와 테이블은 만들지 않는다.** 헥사고날 구조 중 `application/port/in`(UseCase·result), `application/port/out`(조회 포트), `application/service`, `adapter/in/web`, `adapter/out/persistence`만 쓴다.
- 집계는 [ADR-007](007-inventory-query-jpql-cross-domain-join.md)과 같은 방식으로 조회 전용 쿼리(JPQL)가 다른 도메인 테이블을 ID로 직접 조인해 결과 레코드를 만든다. 명령 경로는 없다.
- 결과 레코드는 다른 도메인의 enum을 참조하지 않는다. 상태는 이름(`String`)으로 담는다([#248](https://github.com/2026-KB-WMS/sports-wms-server/issues/248)의 "자기 타입 + 어댑터 변환" 방향과 같다).
- 본사 요약(`summary`)과 추이(`trends`)는 호출을 나눈다. 요약은 홈 진입 때마다 부르므로 가볍게 두고, 월별 추이·순위처럼 범위가 넓은 집계는 따로 부른다.
- 진행중은 현재 시점의 상태 스냅샷, 완료는 완료 시각(입고 `received_at`, 출고 `delivered_at`)이 속한 달 기준으로 센다. 시작 전(입고 `ARRIVED`, 출고 `READY`)과 `CANCELED`는 입출고 집계에서 제외한다.
- **인덱스는 이번에 추가하지 않는다.** 월 범위 조건(`received_at`, `delivered_at`, `requested_at`)에 맞는 인덱스를 미리 만들 수 있지만, 현재 데이터 규모에서는 효과를 측정할 수 없다. 응답 시간이 문제가 되면 V2 이후 마이그레이션으로 추가한다.

## 근거
- 집계는 여러 도메인 데이터를 한 응답에 모으는 것 자체가 목적이라 DB 레벨 조인이 도메인 간 호출 반복보다 효율적이다.
- 독립 패키지로 분리하면 다른 도메인이 대시보드를 몰라도 되고, 조회 전용 결합이 한 곳에 모인다.

## 검토했던 대안
- 기존 도메인(재고 등)에 대시보드 API를 추가 — 기각. 재고가 입고·출고·지점 발주 테이블을 읽는 구조가 되어 소유 경계가 흐려진다.
- 서비스에서 각 도메인 UseCase를 호출해 조합 — 기각. 창고별·월별 반복 호출이 생기고 조합 코드가 커진다.
- 집계 전용 요약 테이블(역정규화) — 기각. 현재 규모에서는 과설계이고 동기화 로직을 따로 관리해야 한다.
- 월 범위 인덱스를 미리 추가 — 보류. 위 결정 참고.

## 영향
- 다른 도메인의 테이블·컬럼명이 바뀌면 대시보드 쿼리도 함께 깨진다. ADR-007과 같은 결합이며 조회 경로에 한정된다.
- 대시보드 도메인에는 `domain/entity`, 마이그레이션이 없다. 새 도메인이지만 `product` 구조를 그대로 따르지는 않는다.
