# ADR-032: 목록 API 페이지네이션·정렬 규칙 — 필요한 목록에만 적용하고, 정렬 필드는 API별 화이트리스트로 제한한다

- 상태: Accepted
- 날짜: 2026-10-16

## 컨텍스트
목록 API는 지금까지 페이지네이션 없이 `data.items`에 전체를 돌려주고, 정렬도 엔드포인트마다 고정이었다(`docs/api/conventions.md`의 "페이지네이션 보류"). 데이터가 늘면 응답이 커지고, 화면이 열 클릭으로 정렬하려 해도 프런트가 받은 한 페이지 안에서만 정렬할 수 있어 결과가 틀려 보인다. 공통 규칙(`page`·`size`·`sort`, `data.pageInfo`)은 이미 `conventions.md`에 정해져 있었고, 이 ADR은 구현 방식을 확정한다. 도메인별 적용은 서브이슈(#289~#294)에서 한다.

## 결정
- **요청**: `page`(1부터, 기본 1), `size`(기본 20, 1~100), `sort`(`필드,asc|desc`, 방향 생략 시 asc). 정렬 기준은 **하나만** 받는다. 범위를 벗어난 `page`·`size`, 허용되지 않은 `sort` 필드·방향·형식은 400 `VALIDATION_ERROR`다. `page`·`size`가 숫자가 아니면 기존대로 400이다.
- **응답**: `data.items`와 `data.pageInfo`(`page`, `size`, `totalElements`, `totalPages`, `sort`). `sort`는 실제 적용된 첫 정렬 기준(`createdAt,desc`)이다. 요청에 `sort`가 없으면 기본 정렬을 내려주므로, 프런트가 API별 기본 정렬을 몰라도 정렬 화살표를 그릴 수 있다. 항목이 없으면 `totalPages`는 0이다.
- **정렬 화이트리스트**: API마다 `SortSpec`을 컨트롤러 상수로 정의한다. 정렬 가능한 필드(API 이름 → 쿼리 경로), 기본 정렬, ID 보조 정렬을 담는다. 쿼리 경로는 JPQL 별칭 경로(`i.createdAt`, 조인한 `w.name` 포함)다. 집계 값(항목 수·총액)은 집계식(`count(l)`, `sum(l.lineAmount)`)을 경로로 쓸 수 있고, `PageAdapter`가 `(`가 들어간 경로만 `JpaSort.unsafe`로 넘긴다. 경로는 서버가 정한 화이트리스트에서만 오므로 사용자 입력이 쿼리에 들어가지 않는다.
- **ID 보조 정렬**: 어떤 정렬이든 마지막에 ID를 첫 정렬과 같은 방향으로 붙인다. 같은 값이 많아도 페이지 사이에 행이 겹치거나 빠지지 않게 하기 위해서다. 한 컬럼으로 행을 구분할 수 없는 집계 목록(구역+SKU 등)은 ID 경로를 여러 개 준다.
- **기본 정렬 유지**: `sort`를 생략하면 그 API의 기존 고정 정렬을 기본값으로 쓴다. 첫 조회 결과는 페이지네이션 도입 전과 같다.
- **적용 대상**: 모든 목록에 붙이지 않는다. 도메인 서브이슈를 시작할 때 그 도메인의 목록을 나열해 적용 대상을 사용자와 정한다. 적용하지 않은 목록은 지금처럼 `data.items`만 돌려주고 `page`·`size`·`sort`를 무시하며, API 문서에 "페이징 없음"으로 적는다.
- **계층 분리**: 페이지 조건·결과는 Spring과 무관한 `PageCondition`·`PageResult`(`common.paging`)로 포트가 주고받는다. Spring Data의 `Pageable`·`Page`로의 변환은 영속성 어댑터의 `PageAdapter`(`common.persistence`)에서만 한다. 응답 포맷은 `common.response.PageResponse`다.
- **전체 건수 쿼리**: 생성자 프로젝션이 `group by`나 집계를 쓰는 쿼리는 Spring Data가 건수 쿼리를 만들 수 없으므로 `countQuery`를 직접 적는다.

## 근거
- 페이징이 있으면 정렬은 서버가 전체 데이터에서 해야 페이지 사이 순서가 맞는다. 정렬 없이 페이징만 넣으면 프런트가 현재 페이지 안에서만 정렬해 틀린 결과를 보여준다.
- 임의 필드를 받으면 잘못된 컬럼명이 500으로 새고 인덱스가 없는 컬럼으로 정렬해 느려질 수 있다. 화이트리스트로 허용 필드를 소수로 고정하고, 필요한 필드는 나중에 추가한다.
- 정렬을 하나만 받으면 화면의 "열 클릭 정렬"과 맞고 검증과 응답 표현이 단순하다.
- 마스터·코드성 목록처럼 데이터가 적은 곳은 페이징이 오히려 화면 구현을 복잡하게 하므로, 필요한 곳에만 붙인다.

## 검토했던 대안
- **Spring Data `Pageable` 파라미터를 컨트롤러에서 바로 받기** — 기각. 허용 필드 제한을 따로 해야 하고, 잘못된 `sort`가 JPA 예외(500)로 새며, 포트가 Spring 타입에 묶인다. 응답의 `pageInfo.sort`도 직접 만들어야 한다.
- **여러 정렬 기준(`sort`를 반복해서 받기)** — 보류. 화면 요구가 없다. 필요해지면 `SortSpec.resolve`를 확장한다.
- **프런트 정렬만 사용** — 페이지네이션 도입 후에는 부정확하다. 전체를 한 번에 받는 소수 목록에만 유효하다.
- **모든 목록 일괄 적용** — 기각. 위 근거대로 필요한 목록에만 적용한다.

## 영향
- 페이지네이션을 적용한 목록의 응답은 `data.pageInfo`가 추가되고 `size` 기본 20 때문에 전체가 아닌 20건만 내려온다. 프런트가 `page`·`size`·`sort`와 `pageInfo`를 처리해야 한다.
- 도메인 서브이슈마다 코드, 테스트, 해당 `docs/api/*.md`를 한 PR에서 바꾼다.
- `common.persistence.PageAdapterIntegrationTest`가 조인한 컬럼 정렬, ID 보조 정렬, 건수 쿼리가 실제 JPQL에서 동작함을 보장하는 기준 예시다. 도메인 쿼리는 같은 모양(생성자 프로젝션 + 별칭 경로 정렬 + `countQuery`)을 따른다.
