# ADR-029: 창고 발주의 공급처는 발주 라인 단위로 배정하고, SKU-공급처는 다대다로 매핑한다

- 상태: Accepted
- 날짜: 2026-10-15

## 컨텍스트
창고 발주(`PurchaseOrder`)는 헤더에 공급처(`supplier_id`)가 하나 붙어 있었고, 창고 관리자가 발주를 등록하면서 공급처를 직접 골랐다. 이 때문에 두 가지 문제가 있었다.

- 창고 관리자가 공급처를 고르려면 공급처 목록을 조회할 수 있어야 해서, 공급처 정보 접근을 막기 어려웠다.
- 한 발주에 공급처가 다른 SKU를 함께 담을 수 없었다. SKU가 어느 공급처에서 오는지는 시스템에 없었고, 창고 관리자의 선택에만 의존했다.

원하는 흐름은 표준 ERP 흐름이다. 창고 관리자는 SKU와 수량만 요청하고, 본사 관리자가 요청 수량의 적정성을 검토해 확정(또는 반려)하면서 공급처를 지정한다.

## 결정
- **공급처는 발주 라인(`purchase_order_line.supplier_id`)에 둔다.** 요청됨 상태의 라인은 공급처가 비어 있고, 본사 관리자가 확정할 때 라인마다 지정한다. 한 발주 안에 공급처가 여러 개일 수 있고, 발주서를 공급처별로 쪼개지 않는다.
- **SKU↔공급처는 다대다 매핑(`sku_supplier`)으로 둔다.** (SKU, 공급처) 쌍은 유일하다. 확정 때 지정할 수 있는 공급처는 해당 SKU에 매핑된 공급처뿐이다. 매핑은 공급처를 소유한 `inbound` 도메인에 두고 SKU는 `Long skuId`로만 참조한다([ADR-005](005-entity-reference-by-id.md)).
- **초기에는 본사가 확정 시 공급처를 직접 고른다.** 기본 공급처(`isPrimary`)를 도입해 자동 배정하는 것은 후속이다. 확정이 "라인별 공급처"를 받는 형태라 자동 배정은 그 값을 기본값으로 채우는 것만으로 붙는다.
- **완료는 입고로 자동 처리한다.** 라인은 입고 수량이 예정 수량 이상이면 완료되고, 모든 라인이 완료되면 발주 마스터가 완료된다. 공급처 단위 완료는 그 공급처의 라인이 모두 완료된 것으로 계산하며 새 상태나 엔티티를 두지 않는다.
- **본사 반려 전이를 추가한다.** `REQUESTED → REJECTED`, 본사 관리자만 가능하다. 사유와 상태 이력을 남긴다.
- **입고는 공급처 단위로 등록한다.** 공급처별로 물건이 따로 도착하므로 입고(`inbound`)에 공급처를 두고, 해당 공급처의 라인만 입고 대상으로 한다.

## 근거
- 라인 단위로 두면 발주를 쪼개는 방식(원본 재사용 또는 새 발주서 생성)에서 생기는 번호 부여와 이력 연결 문제가 없다. 완료 규칙도 기존 라인·마스터 완료 규칙을 그대로 쓴다.
- 다대다는 같은 SKU를 여러 공급처에서 들이는 현실을 담으면서, 지정 가능한 후보를 제한해 잘못된 공급처가 들어가는 것을 막는다.
- 확정 API가 라인별 공급처를 받는 모양을 처음부터 쓰면 자동 배정 도입 때 API 모양이 바뀌지 않는다.

## 검토했던 대안
- **확정 시 공급처별로 발주서를 쪼갬**(원본 한 묶음 재사용 + 나머지 새로 생성, 또는 요청 엔티티를 따로 두고 확정 발주서를 전부 새로 생성) — 기각. 새 발주 번호와 원본·분할 관계를 관리해야 하고, 요청 엔티티를 따로 두면 모델이 커진다.
- **SKU에 공급처 하나를 직접 연결**(`product_sku.supplier_id`) — 기각. 한 SKU를 여러 공급처에서 들이는 경우를 담지 못한다.
- **마스터에 공급처를 유지하고 한 발주에는 한 공급처만 허용** — 기각. 창고 관리자가 SKU별 공급처를 알고 발주를 나눠서 올려야 해서 요청 흐름이 달라지지 않는다.
- **공급처 단위 완료를 수동 처리** — 기각. 입고 수량으로 이미 라인·마스터 완료가 계산되며, 수동 단계는 새 상태와 API만 늘린다.

## 영향
- **API(breaking)**: `POST /purchase-orders`에서 `supplierId`가 빠지고, 확정 요청이 라인별 공급처를 받으며, 반려 API가 생긴다. 발주 응답은 라인별 공급처와 공급처 목록을 내려준다. 클라이언트에 영향이 있다.
- **DB**: `sku_supplier` 신설, `purchase_order_line.supplier_id`와 `inbound.supplier_id` 추가, 기존 발주·입고의 공급처 복사, 기존 발주에서 쓰인 (SKU, 공급처) 조합을 매핑으로 이전한다. `purchase_order.supplier_id` 제거와 `inbound.supplier_id`의 NOT NULL 강화는 서비스가 새 컬럼을 쓰게 된 뒤 별도 마이그레이션에서 한다(레이어별 PR 사이에 빌드를 유지하기 위해).
- **재고**: 로트의 공급처는 입고 라인이 속한 발주 라인의 공급처를 기준으로 한다.
- **공급처 비활성화**: 진행 중 발주 확인이 헤더가 아니라 라인의 공급처 기준으로 바뀐다.
- **문서 갱신**: `api/inbound.md`, `domain/inbound.md`, `api/authorization.md`는 서비스·웹 레이어 PR(#269, #270)에서 갱신한다.
- **범위 밖**: 기본 공급처 자동 배정, 안전 재고 알림, 공급처에 발주서를 전달하는 기능.
