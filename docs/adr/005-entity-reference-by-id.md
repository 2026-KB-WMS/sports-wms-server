# ADR-005 엔티티 참조는 도메인 구분 없이 전부 ID 참조 (Long xxxId)

## 상태
`Accepted` (2026-09-22, 개정)

## 컨텍스트
엔티티 간 연관관계를 JPA에서 어떻게 표현할지(전부 FK 객체 참조 vs ID만 보관) 기준이 없었다. 도메인별 패키지 + 헥사고날 아키텍처로 개발 중인데, 다른 도메인 엔티티를 `@ManyToOne` 등으로 직접 참조하면 패키지 경계가 사실상 무너지는 문제가 있었다.
최초 결정(같은 도메인은 FK 객체 참조, 다른 도메인은 ID 참조)은 이후 product 도메인(#17, #18)을 실제로 구현하는 과정에서 같은 도메인 내부에서도 전부 `Long xxxId`로 구현되었고, 개인 프로젝트라 여러 개발자 간 합의를 맞출 필요가 없다는 점을 고려해 기준을 단순화하기로 했다.

## 결정
같은 도메인 내부이든 다른 도메인(패키지)이든 구분 없이, 모든 엔티티 참조는 `Long xxxId` 형태의 ID 값만 보관한다. JPA 연관관계 매핑(`@ManyToOne`, `@OneToMany` 등)은 사용하지 않는다. 실제 데이터가 필요하면 해당 도메인의 레포지토리/서비스를 통해 조회한다.

## 근거
- 도메인 모델(순수 POJO, 프레임워크 의존 없음)이 이미 모든 관계를 ID로 표현하므로, 영속성 계층(JPA 엔티티)도 동일한 방식으로 맞춰 매핑을 단순하게 유지한다.
- 객체 참조 시 생길 수 있는 지연 로딩 프록시·N+1 문제를 도메인 경계 안쪽에서도 피할 수 있다.
- 참조 규칙이 "같은 도메인이냐 아니냐"를 구분할 필요 없이 단일 기준이 되어 구현·코드리뷰가 단순해진다.
- 향후 특정 도메인을 별도 DB나 서비스로 분리할 가능성을 열어둘 수 있다.
- ID 참조는 DDD의 "애그리거트는 다른 애그리거트를 ID로만 참조한다" 원칙과도 일치한다.

## 검토했던 대안
- 같은 도메인 내부는 FK 객체 참조, 다른 도메인은 ID 참조 (최초 결정) — 폐기. 도메인 내부/외부에 따라 참조 방식이 갈리면서 규칙이 이원화되고, 실제 구현(product 도메인)에서도 같은 도메인 내부 참조를 ID로 처리하는 편이 더 자연스러웠다.
- 모든 참조를 FK 객체 참조로 통일 — 기각. 구현은 단순하지만 도메인 간 결합도가 높아지고 트랜잭션 범위가 의도치 않게 여러 도메인으로 번질 위험이 있다.

## 영향
- ERD 데이터 사전: "참조 규칙" 섹션을 "같은 도메인/다른 도메인 구분 없이 ID 참조"로 갱신 완료
- 이미 구현된 product 도메인(#17, #18)은 변경 없이 이 기준과 일치
- 앞으로 나머지 도메인(warehouse, inbound 등)도 이 기준(전부 Long ID 참조)을 따른다
- 조회 전용 API의 예외는 [ADR-007](007-inventory-query-jpql-cross-domain-join.md), 복합키 예외는 [ADR-009](009-sku-option-value-embedded-id.md) 참고
