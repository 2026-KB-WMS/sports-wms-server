# ADR-013: 최초 본사 관리자는 시작 시 환경변수로 생성

- 상태: Accepted
- 날짜: 2026-10-08

## 컨텍스트
가입 API는 `HQ_ADMIN`을 만들 수 없고, 가입 승인과 계정 관리(`/users`)는 `HQ_ADMIN`만 할 수 있다. 그래서 새 환경에서는 DB에 직접 첫 관리자를 넣어야 했다. 정책 자체는 #162에서 "관리자가 하나도 없을 때만 환경변수로 시작 시 생성"으로 정했지만 구현이 빠져 있었다(#189).

## 결정
- 앱이 뜰 때 `InitialHqAdminRunner`(`auth.adapter.in.startup`, `ApplicationRunner`)가 `UserUseCase.ensureInitialHqAdmin`을 호출한다. 서비스는 `HQ_ADMIN`이 하나라도 있으면 아무것도 하지 않고(`ALREADY_EXISTS`), 없고 설정이 모두 비어 있으면 만들지 않으며(`NOT_CONFIGURED`), 설정이 있으면 `ACTIVE` 관리자를 만든다(`CREATED`).
- 설정은 `wms.admin.{login-id,password,name,email,phone}`이며 환경변수 `WMS_ADMIN_LOGIN_ID`, `WMS_ADMIN_PASSWORD`, `WMS_ADMIN_NAME`, `WMS_ADMIN_EMAIL`, `WMS_ADMIN_PHONE`로 받는다. 기본값은 모두 비어 있다. `docker-compose.yml`은 `.env`의 값을 그대로 넘기고, 레포에는 비밀번호를 두지 않는다(`.env.example`에는 빈 키만 있다).
- 로그인 아이디(소문자 4~20자)와 비밀번호(8자 이상, 영문·숫자·특수문자, 72바이트 이하)는 가입과 같은 규칙으로 검사하고, 이름·이메일·연락처는 비어 있지 않은지와 컬럼 길이를 본다. 일부만 설정했거나 규칙을 어기면 기동을 막지 않고 오류 로그만 남긴다. 아이디·이메일이 이미 다른 계정에 쓰이면 409로 거절되어 같은 방식으로 로그만 남긴다.
- 서버가 여러 대 동시에 뜨면 "관리자 없음 확인 후 저장" 사이에 경쟁이 생길 수 있다. 최종 방어선은 `uk_users_login_id`·`uk_users_email` 유니크 제약이며, 러너는 이때 나는 `DataIntegrityViolationException`을 "다른 인스턴스가 먼저 만들었다"로 보고 넘어간다.
- 비밀번호는 로그와 응답 어디에도 남기지 않는다(로그에는 로그인 아이디만).

## 근거
- 이미 있는 `User.createHqAdmin`과 `existsByRole`이 이 용도로 만들어져 있어 새로 짜는 코드가 작다.
- 설정을 환경변수로만 받으면 비밀번호가 레포나 이미지에 들어가지 않고, 배포 환경마다 다르게 둘 수 있다.
- 기동을 막지 않으면 설정 실수 때문에 앱 전체가 안 뜨는 일이 없고, 이미 관리자가 있는 환경은 설정을 지워도 영향이 없다.

## 검토했던 대안
- Flyway 시드: 비밀번호 해시가 레포에 들어가 모든 환경이 같은 초기 비밀번호를 갖게 되어 제외.
- DB에 직접 입력(기존 상태): 해시를 직접 만들어야 해서 실수하기 쉽고 절차가 문서에만 남아 제외.
- 별도 CLI·관리 스크립트: 운영 절차가 하나 더 생기고 코드(규칙 검증)를 재사용하기 어려워 제외.

## 영향
- 환경변수의 비밀번호는 관리자가 없을 때 첫 생성에만 쓰인다. 이후 값을 바꿔도 반영되지 않고, 비밀번호 변경 API가 없어서(보류) 지금은 관리자가 비밀번호를 바꿀 방법이 없다.
- 설정을 지워도 만들어진 관리자는 그대로다. 관리자를 모두 비활성화해도 `HQ_ADMIN` 행이 남아 있으므로 다시 만들어지지 않는다.
- 모든 `@SpringBootTest`가 시작 시 `existsByRole` 쿼리를 한 번 실행한다(설정이 비어 있으면 아무것도 만들지 않는다).
