# ADR-020: 주소를 입력받는 엔티티에 위도·경도를 선택 필드 쌍으로 저장한다

- 상태: Accepted
- 날짜: 2026-10-12

## 컨텍스트
프론트가 주소를 지도 API로 입력하도록 바뀌면서, 주소와 함께 위도·경도를 서버에 저장해야 한다. 창고·지점·공급처는 `address` 문자열만 갖고 있어 좌표가 없다. 이미 저장된 행은 좌표 없이 존재한다.

## 결정
- **대상**: 주소를 입력받는 엔티티 전부(창고, 지점, 공급처). 사용자·구역 등 주소가 없는 엔티티는 제외한다.
- **컬럼**: `latitude`, `longitude` `DECIMAL(10,7)` NULL 허용. 소수 7자리는 약 1cm 정밀도이며, 위도(±90)와 경도(±180)를 모두 담는다.
- **선택 필드**: 등록·수정 요청의 `latitude`, `longitude`는 선택이다. 기존 데이터에 좌표가 없으므로 필수로 하지 않는다.
- **쌍으로만**: 한쪽만 보내면 400 `VALIDATION_ERROR`다. 한쪽만 있는 좌표는 의미가 없다.
- **범위**: 위도 -90~90, 경도 -180~180을 벗어나면 400이다.
- **정밀도**: 소수 7자리를 넘는 값은 거절하지 않고 반올림해 저장한다. 지도 API가 double을 그대로 넘기는 경우가 많다.
- **수정**: 좌표를 생략하면 기존 값을 유지한다. 주소만 바꿔도 좌표는 그대로이므로, 주소를 바꿀 때는 호출자가 좌표도 함께 보내야 한다. 좌표를 비우는 방법은 두지 않는다.
- **응답**: 단건·목록 응답에 `latitude`, `longitude`를 추가하고, 값이 없으면 `null`이다.

## 근거
- 기존 행을 일괄 변환할 방법이 없으므로(주소 문자열에서 좌표를 서버가 계산하지 않는다) NULL 허용이 마이그레이션의 유일한 안전한 선택이다.
- 쌍 검증을 두어 위도만 있고 경도가 없는 불완전한 좌표가 저장되는 것을 막는다.
- 반올림은 클라이언트가 자릿수를 맞추지 않아도 되게 하고, 저장 정밀도를 일정하게 유지한다.

## 검토했던 대안
- 좌표를 필수로 하고 기존 행을 0,0으로 채우기: 기각. (0,0)은 실제 위치(기니만 앞바다)라 "없음"과 구분되지 않는다.
- 서버가 주소로 지오코딩해서 좌표를 채우기: 기각. 외부 API 의존과 키 관리가 생기고, 프론트가 이미 지도 API로 좌표를 얻는다.
- 소수 7자리 초과 시 400: 기각. 정밀도 문제로 요청을 거절하는 것은 클라이언트에 불필요한 부담이다.
- 좌표를 별도 테이블로 분리: 기각. 주소와 항상 같이 읽고 쓰며, 조인만 늘어난다.
- 주소 변경 시 좌표 자동 초기화: 기각. 주소만 오타 수정하는 요청에서 좌표를 잃게 된다.

## 영향
- 마이그레이션 `V17__add_geo_coordinates.sql`: `warehouse`, `store`, `supplier`에 컬럼 추가.
- 코드: 도메인 엔티티·JPA 엔티티, 등록·수정 커맨드와 요청 DTO, 서비스, 목록·단건 응답. 기존 생성자는 좌표 없는 형태를 그대로 쓸 수 있게 유지했다.
- 명세: `api/warehouse.md`, `store.md`, `inbound.md`, `conventions.md`.
- `GET /warehouses/my`, `GET /stores/my`의 소속 응답에는 이번에 좌표를 넣지 않았다. 필요하면 후속으로 추가한다.
