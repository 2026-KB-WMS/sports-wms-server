# ADR-030: 창고 발주 요청과 공급처 발주서를 분리한다

- 상태: Accepted
- 날짜: 2026-10-15
- 관계: [ADR-029](029-purchase-order-line-supplier.md)의 "공급처를 발주 라인에 배정하고 발주서를 쪼개지 않는다"와 "입고는 공급처 단위로 등록한다", "진행 중 입고 제한은 (발주, 공급처) 단위" 부분을 이 결정으로 대체한다. ADR-029의 SKU↔공급처 다대다 매핑, 본사 확정 시 공급처 선택, 반려 전이, 기본 공급처 자동 배정을 후속으로 두는 결정은 그대로 유효하다.

## 컨텍스트
본사가 공급처에 내는 발주는 **공급처당 한 건**이다. 반면 창고 관리자의 요청에는 여러 공급처의 SKU가 함께 들어갈 수 있다. ADR-029는 요청 한 건(`PurchaseOrder`) 안에서 라인마다 공급처를 두는 것으로 이 둘을 한 덩어리로 다뤘다. 그 결과 다음이 어색해졌다.

- 입고가 요청 한 건에 연결되는데 도착하는 물건은 한 공급처 몫뿐이라, 입고에 공급처를 따로 붙이고 입고 등록 때 공급처를 골라야 했다.
- 진행 중 입고 제한, 공급처 단위 완료 같은 규칙을 "요청 + 공급처" 조합으로 계산해야 했다.
- 공급처에 낸 발주 한 건을 가리키는 번호나 상태가 없었다.

## 결정
- **창고 발주 요청**(`purchase_order`, `purchase_order_line`)은 그대로 둔다. 창고 관리자가 SKU와 수량만 요청하고 여러 공급처가 섞일 수 있다. 상태는 `REQUESTED → CONFIRMED → COMPLETED`, `REQUESTED·CONFIRMED → CANCELED`, `REQUESTED → REJECTED`다.
- **공급처 발주서**(`supplier_order`)를 신설한다. 본사가 요청을 확정할 때 공급처당 한 건이 자동으로 만들어지고, `(요청, 공급처)` 쌍은 유일하다.
  - 번호는 `SO-yyyyMMdd-NNNN`(서버 생성, 유일)이다.
  - 상태는 `ISSUED`(생성) → `PARTIALLY_RECEIVED`(일부 입고 완료) → `COMPLETED`(전량 입고), 요청 취소 시 `CANCELED`다.
  - 발주서 상세 테이블은 따로 두지 않는다. 요청 상세 라인이 `supplier_order_id`로 발주서에 연결되며, 라인의 `supplier_id`는 발주서의 공급처와 항상 같다.
- **확정**: 본사 관리자가 라인별 공급처를 지정한다(해당 SKU에 매핑된 활성 공급처, 모든 라인 필수). 서버는 공급처별로 발주서를 만들고 라인을 연결한 뒤 요청을 `CONFIRMED`로 바꾼다.
- **입고**: 공급처 발주서 한 건에 연결한다. 입고 등록은 `supplierOrderId`를 받고, 발주서가 `ISSUED`·`PARTIALLY_RECEIVED`일 때만 등록할 수 있다. 같은 발주서에 `ARRIVED`·`INSPECTING` 입고가 있으면 409 `INBOUND_IN_PROGRESS`이고, 다른 발주서의 입고는 병렬로 진행할 수 있다. 검수는 그 발주서에 속한 라인만 대상으로 한다.
- **완료 전파**: 라인은 누적 입고 수량이 예정 수량 이상이면 `COMPLETED`다. 발주서는 첫 입고 완료 때 `PARTIALLY_RECEIVED`, 소속 라인이 모두 완료되면 `COMPLETED`다. 모든 발주서가 완료되면 요청이 `COMPLETED`다. 별도의 수동 완료 API는 없다.
- **취소·반려**: 취소는 요청 단위로만 하고 발주서도 함께 `CANCELED`가 된다. 취소되지 않은 입고가 있는 발주서가 있으면 409 `PURCHASE_ORDER_HAS_INBOUND`다. 반려는 `REQUESTED`에서만 가능하며 발주서가 생기기 전이다.
- **조회**: `GET /supplier-orders`와 `GET /supplier-orders/{supplierOrderId}`를 둔다. 창고 관리자는 담당 창고의 발주서만 본다.
- **공급처 비활성화 가드**: 진행 중 발주서(`ISSUED`·`PARTIALLY_RECEIVED`) 기준으로 판단한다.
- **공급처에 전달했는지 기록하는 상태는 두지 않는다.** 전달은 시스템 밖에서 하며, 필요해지면 발주서에 상태나 일시를 추가한다.

## 근거
- 본사의 업무 단위(공급처당 발주 한 건)가 그대로 데이터 단위가 되어, 입고·완료·취소 규칙이 요청과 공급처 조합을 계산하지 않고 발주서 하나만 보면 된다.
- 발주서 상세를 별도 테이블로 두지 않고 라인에 연결만 하면, 이미 구현된 라인 수량·상태 로직과 입고 검수 로직을 그대로 쓴다.
- 입고가 발주서에 연결되므로 입고 등록 때 공급처를 따로 판단하는 로직이 필요 없다.

## 검토했던 대안
- **ADR-029 유지(요청 한 건 안에서 라인별 공급처, 발주서 없음)** — 기각. 위 컨텍스트의 어색함이 규칙마다 반복된다. 공급처 발주를 가리키는 번호·상태도 만들 수 없다.
- **확정 때 요청 자체를 쪼개 새 요청을 만듦(원본 재사용 + 나머지 새로 생성)** — 기각. 창고가 올린 요청이 여러 건으로 바뀌어 요청과 결과의 대응이 흐려진다. 요청을 그대로 두고 그 아래에 발주서를 두는 편이 추적이 쉽다.
- **발주서 상세 테이블을 따로 둠** — 기각. 라인과 일대일이라 중복이다.
- **여러 요청을 합쳐 공급처 한 곳에 한 발주서로 냄** — 이번에는 제외. 지금 구조(발주서가 요청 한 건에 속함)는 이 확장을 막지 않는다. 필요해지면 발주서가 요청에 속하는 관계를 바꾼다.

## 영향
- **API(breaking)**: `POST /purchase-orders`에서 `supplierId`가 빠지고, 확정 요청이 라인별 공급처를 받으며, 반려 API와 `GET /supplier-orders`가 생긴다. `POST /inbounds`는 `purchaseOrderId` 대신 `supplierOrderId`를 받는다. 발주·입고 응답이 바뀐다. 클라이언트에 영향이 있다.
- **DB**: `supplier_order` 신설, `purchase_order_line.supplier_order_id`와 `inbound.supplier_order_id` 추가, 기존 확정·완료·취소 요청의 발주서 생성과 연결, 이후 `purchase_order.supplier_id`와 `inbound.supplier_id` 제거. 레이어별 PR 사이에 빌드를 유지하려고 제거는 서비스 전환 이후 마이그레이션에서 한다.
- **재고**: 로트의 공급처는 발주서의 공급처를 따른다.
- **문서**: `api/inbound.md`, `domain/inbound.md`, `api/authorization.md`에 개편 내용을 반영한다(이 ADR과 같은 PR은 목표 명세를, 이후 구현 PR은 구현 대비 메모를 갱신).
- **범위 밖**: 기본 공급처 자동 배정, 안전 재고 알림, 발주서 전달 상태, 여러 요청을 합친 발주서.
