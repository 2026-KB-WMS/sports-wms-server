# ADR-023: 브랜드 코드는 영문 3자 직접 입력이며, 기존 브랜드는 코드 없이 두고 한 번만 지정할 수 있다

- 상태: Accepted
- 날짜: 2026-10-13

## 컨텍스트
브랜드는 이름(`name`)만 가지고 있어 코드로 식별할 수 없다. 상품·창고·지점 등 다른 마스터는 코드를 갖는다. 이미 등록된 브랜드가 있어 코드를 일괄 채울 방법이 없다.

## 결정
- **컬럼**: `brand.brand_code VARCHAR(3)`, UNIQUE(`uk_brand_code`), NULL 허용. 기존 브랜드는 NULL로 남는다(MySQL UNIQUE는 NULL 여러 개를 허용한다).
- **형식**: 영문 3자(`^[A-Za-z]{3}$`). 서버가 대문자로 정규화해 저장하므로 `nik`과 `NIK`는 같은 코드다.
- **직접 입력**: 등록 요청의 `brandCode`는 필수이며 사람이 입력한다. 형식 위반은 400 `VALIDATION_ERROR`, 중복은 409 `DUPLICATE_BRAND_CODE`(DB 유니크 위반도 동일 매핑).
- **수정**: 코드는 등록 후 바꿀 수 없다. 단, 코드가 없는 기존 브랜드에는 수정 요청으로 한 번 지정할 수 있다. 이미 코드가 있으면 400이다.
- **응답·검색**: 등록·목록·수정 응답에 `brandCode`를 추가하고(없으면 `null`), 목록 `keyword`는 코드도 검색한다.
- **규칙 위치**: 형식 검사는 요청 DTO와 서비스 양쪽에서 한다. 서비스 검사는 웹을 거치지 않는 호출도 같은 규칙을 지키게 한다.

## 근거
- 코드를 필수 컬럼으로 만들 수 없다. 기존 행을 의미 있는 값으로 채울 방법이 없고, 임의 값은 코드 체계를 오염시킨다.
- 3자 코드는 대소문자 구분 없이 같게 다루는 편이 입력 실수(소문자)로 인한 중복을 막는다.
- 기존 브랜드의 코드를 영영 비워 둘 수 없으므로 한 번 지정은 허용하되, 지정 후 변경은 다른 코드와 같은 규칙(등록 후 수정 불가)을 따른다.

## 검토했던 대안
- 서버 자동 발급: 기각. 코드가 브랜드를 알아볼 수 있는 약어(예: NIK)여야 해서 사람이 정한다.
- 코드를 영구 불변으로 하고 기존 브랜드는 코드 없이 두기: 기각. 기존 브랜드가 코드를 가질 방법이 없다.
- 코드 수정을 항상 허용: 기각. 코드를 참조하는 곳(라벨·외부 문서)이 생길 수 있어 다른 코드와 같이 불변으로 둔다.
- 기존 행을 이름 기반 임의 코드로 일괄 채우기: 기각. 의미 없는 코드가 들어가고 충돌을 서버가 해결해야 한다.

## 영향
- 마이그레이션 `V19__add_brand_code.sql`.
- 코드: `Brand`·`BrandJpaEntity`, 등록·수정 커맨드·요청·응답, `BrandService`, `ProductErrorCode.DUPLICATE_BRAND_CODE`.
- 명세: `api/product.md`. 프론트: 브랜드 등록 화면에 코드 입력란(영문 3자)을 추가하고, 코드가 없는 기존 브랜드는 수정 화면에서 지정하게 한다.
