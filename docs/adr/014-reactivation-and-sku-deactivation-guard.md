# ADR-014 재활성화 API는 상위 확인 후 허용하고, SKU 비활성화에도 사용 중 가드를 둔다

## 상태
`Accepted` (2026-10-10)

## 컨텍스트
창고·구역·지점·공급처는 비활성화만 있고 다시 활성화하는 API가 없었다. 잘못 비활성화하면 DB를 직접 고쳐야 했고, 명세에도 "재활성화 방법"이 미결로 남아 있었다. 또 상품 비활성화는 재고·진행 중 업무가 있으면 `PRODUCT_IN_USE`로 막히지만, SKU 단건 비활성화(`PATCH /products/skus/{skuId}/status`)에는 같은 검사가 없어 상품 단위로는 막히는 상태가 SKU 단위로는 뚫렸다.

## 결정
- 창고·구역·지점·공급처에 `PATCH .../{id}/activate`를 추가한다(HQ_ADMIN, 본문 없음). 이미 ACTIVE면 409 `CONFLICT`.
- **구역은 상위가 활성일 때만** 활성화한다. 소속 창고가 비활성이거나 상위 구역이 비활성이면 409 `CONFLICT`. 창고·지점·공급처는 조건 없이 활성화한다.
- 창고를 활성화해도 구역은 자동으로 활성화하지 않는다(상품과 SKU의 관계와 같다). 구역은 개별로 복구한다.
- 지점 활성화는 비활성화와 같이 `StatusHistory`(`INACTIVE`→`ACTIVE`, 처리자)에 기록한다. 사유는 받지 않는다.
- SKU 비활성화는 활성 SKU에 한해 `isSkuInUse`(재고 보유·할당 > 0, 진행 중 입고·창고 발주·출고·지점 발주)를 확인하고, 해당하면 409 `SKU_IN_USE`로 거절한다. 이미 비활성인 SKU에 다시 비활성화를 요청하면 검사 없이 성공한다.
- 상품 비활성화가 하위 SKU를 함께 비활성화할 때는 상품 단위 검사를 이미 거쳤으므로 SKU 검사를 다시 하지 않는다.

## 근거
- 비활성 창고 아래 활성 구역, 비활성 상위 구역 아래 활성 하위 구역은 "비활성 창고에는 구역을 등록할 수 없다", "비활성 상위 구역에는 하위 구역을 등록할 수 없다"는 기존 등록 규칙과 모순된다. 활성화 때 같은 기준을 적용해 일관되게 유지한다.
- 구역을 창고와 함께 자동 활성화하면 비활성화 당시 일부러 꺼 둔 구역까지 켜진다. 상품 재활성화가 SKU를 자동 복구하지 않는 기존 규칙과 맞춘다.
- SKU 가드가 없으면 재고 도메인은 SKU 상태만 신뢰하므로, 재고가 남은 SKU를 비활성화해 이후 재고 변동이 `SKU_NOT_ACTIVE`로 막히는 상태를 만들 수 있다.

## 검토했던 대안
- 재활성화에 조건을 두지 않음 — 기각. 비활성 창고 아래 활성 구역이 생겨 등록 규칙과 어긋난다.
- 창고 활성화 때 구역도 함께 활성화 — 기각. 개별로 꺼 둔 구역을 의도치 않게 켠다.
- 재활성화를 `PATCH /{id}`의 `isActive`로 처리 — 기각. 기존 수정 API는 `isActive`를 400으로 거절하고 상태 변경은 별도 경로로 둔다는 규칙을 깨고, 지점 이력 기록 같은 부수 효과를 분리하기 어렵다.
- SKU 검사를 상품 단위 쿼리 재사용으로 처리(상품의 SKU 전체 확인) — 기각. 같은 상품의 다른 SKU가 쓰이는 것만으로 이 SKU를 막게 된다.

## 영향
- `ProductUsagePort`에 `isSkuInUse(skuId)`가 추가되고, `ProductUsageAdapter`의 쿼리는 상품·SKU 단위가 같은 JPQL을 조건만 바꿔 쓴다.
- `ProductErrorCode.SKU_IN_USE`가 추가된다.
- 검사와 변경 사이에 새 재고·발주가 생기는 경합은 상품 비활성화와 마찬가지로 막지 않는다(행을 잠그지 않음).
- 브랜드·카테고리·옵션 값은 비활성화 API가 없고 이번에도 추가하지 않는다.
- 문서 갱신: `api/warehouse.md`, `api/store.md`, `api/inbound.md`, `api/product.md`, `domain/deactivation.md`.
