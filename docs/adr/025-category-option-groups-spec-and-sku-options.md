# ADR-025: 카테고리별 옵션 그룹 지정으로 상품 스펙(SPEC)과 SKU 옵션을 구분하고 SKU를 검증·자동 명명한다

- 상태: Accepted
- 날짜: 2026-10-13

## 컨텍스트
라켓의 밸런스·샤프트 강도처럼 상품 하나에 값이 정해지는 속성과, 무게 등급·그립·색상처럼 SKU마다 달라지는 속성이 구분 없이 같은 옵션 그룹으로만 다뤄졌다.

- 카테고리와 옵션 그룹의 관계가 없어 SKU에 어떤 옵션이 필요한지 서버가 알 수 없었다. 옵션은 SKU 등록 뒤 별도 API로 연결해서 누락을 막을 방법이 없었다.
- SKU 코드·이름을 매번 직접 입력하고, 같은 옵션 조합의 SKU가 중복 등록될 수 있었다(명세 미결 항목).
- 옵션 값에 코드가 없어 SKU 코드를 옵션에서 만들 수 없었다.

## 결정
- **카테고리-옵션 그룹 지정**(`category_option_group`): 카테고리마다 옵션 그룹을 `SPEC` 또는 `SKU`로 지정한다. 한 카테고리에서 같은 그룹은 한 번만 지정한다. 옵션 그룹 마스터 자체는 용도를 갖지 않는다.
- **상속**: 하위 카테고리는 상위 카테고리의 지정을 상속한다. 같은 그룹이 여러 단계에 있으면 가까운 카테고리의 지정이 우선한다(용도·순서 모두). 지정은 `PUT /products/categories/{id}/option-groups`로 자신의 지정을 통째로 교체한다.
- **옵션 값 코드**: `option_value.option_code`(영문·숫자 1~10자, 대문자 저장, 그룹 내 unique)를 신규 값 등록에서 필수로 받는다. 기존 값은 `NULL`로 두고 수정 API는 만들지 않는다.
- **상품 스펙**(`product_spec`): 상품 등록·수정에서 `specOptionValueIds`로 받는다. 카테고리의 `SPEC` 그룹마다 값을 하나씩 채워야 하며, 수정은 전체 교체다. 스펙은 상품에만 저장하고 SKU로 복사하지 않는다.
- **SKU 옵션**: SKU 등록이 `optionValueIds`를 같은 트랜잭션에서 받아 `sku_option_value`에 저장한다. 카테고리의 `SKU` 그룹마다 값을 하나씩 채워야 한다.
- **조합 중복**: 같은 상품의 다른 SKU(비활성 포함)와 옵션 값 집합이 같으면 409 `DUPLICATE_SKU_OPTION_COMBINATION`이다. 옵션이 없는 SKU끼리도 같은 조합으로 본다.
- **자동 코드·이름**: `skuCode`·`skuName`을 생략하면 `상품코드-옵션코드…`(카테고리 지정 순서), `상품명 (옵션값/옵션값)`으로 만든다. 직접 입력은 그대로 쓴다. 코드가 없는 값이 섞였거나 길이(50자·200자)를 넘으면 400이며 직접 입력하게 한다.
- **기존 옵션 연결 API**(`POST /products/skus/{id}/options`)는 옵션이 없는 SKU에 한 번만, 등록과 같은 검증을 거쳐 연결하도록 제한한다. 기존 SKU 보완용으로만 남긴다.
- **카테고리 변경 잠금**: 스펙이나 SKU가 있는 상품의 카테고리는 바꿀 수 없다(409 `PRODUCT_CATEGORY_LOCKED`). 스펙·옵션이 카테고리의 지정에 맞춰 만들어지기 때문이다.
- **검증 시점**: 지정과 검증은 등록·수정 시점에만 적용한다. 지정을 바꿔도 저장된 상품·SKU는 건드리지 않는다.
- **기준 데이터 시드**: Flyway `V23__seed_option_master_data.sql`이 스포츠 용품 카테고리 8개(라켓, 셔틀콕, 신발, 의류, 가방, 스트링, 그립, 보호대), 옵션 그룹 10개와 값(코드 포함), 카테고리별 SPEC·SKU 지정을 넣는다. `INSERT IGNORE`라서 같은 코드·이름·값이 이미 있으면 건너뛰고 기존 데이터는 바꾸지 않는다. 용도 지정은 초기값이며 이후 API로 바꿀 수 있다.

## 근거
- 옵션이 어느 단계의 값인지(상품 공통 vs SKU별)를 카테고리가 정해야 서버가 필수 누락과 중복 조합을 막을 수 있다.
- 용도를 옵션 그룹 마스터가 아니라 카테고리 지정에 두면 같은 그룹("무게")이 카테고리에 따라 스펙이 되기도 SKU 옵션이 되기도 한다.
- 지정 단위로 상속을 두면 하위 카테고리마다 같은 그룹을 반복 등록하지 않아도 된다. 가까운 지정 우선 규칙은 상위 지정을 하위에서 재정의하는 가장 단순한 방법이다.
- 코드를 옵션 값에 두면 SKU 코드가 상품과 옵션으로만 결정되어 사람이 입력한 임의 코드의 표기 차이를 줄인다.
- 인벤토리·입고·출고는 `sku_id`만 참조하므로 SKU 등록 입력이 바뀌어도 다른 도메인은 영향이 없다.

## 검토했던 대안
- 지정을 말단 카테고리에만 두기: 기각. 상품이 어느 단계 카테고리에도 붙을 수 있어 말단 한정이 맞지 않고, 하위마다 반복 입력이 필요하다.
- 옵션 그룹 마스터에 용도(SPEC·SKU) 컬럼 두기: 기각. 같은 그룹이 카테고리별로 다른 용도를 가질 수 없다.
- SKU에 상품 스펙 값 복사: 기각. 값이 두 곳에 있으면 스펙 수정이 SKU와 어긋난다. 조회에서 상품의 스펙을 함께 본다.
- 시작 시 `ApplicationRunner`로 시드 넣기: 기각. 실행마다 존재 여부를 검사해야 하고 스키마 변경과 이력이 분리된다. 마이그레이션은 한 번만 실행되고 버전으로 남는다.
- 옵션 코드 수정 API 추가: 이번 범위에서 제외. 기존 값은 SKU 코드를 직접 입력해 쓸 수 있다.
- 연결 API 제거: 기각. 이미 저장된 옵션 없는 SKU를 보완할 방법이 없어진다.

## 영향
- 마이그레이션: `V20__add_option_value_code.sql`(`option_value.option_code`), `V21__create_category_option_group.sql`, `V22__create_product_spec.sql`, 시드 `V23__seed_option_master_data.sql`.
- 코드: `CategoryOptionGroup`·`ProductSpec`·`OptionType`, `CategoryOptionResolver`(상속 계산), `OptionSelectionResolver`(선택 검증), `ProductService`·`ProductSkuService`, `CategoryOptionGroupController`, `GET /products/option-groups`.
- 명세: `api/product.md`. 프론트: 옵션 값 등록에 `optionCode` 입력, 카테고리 옵션 그룹 지정 화면, 상품 등록에 스펙 입력, SKU 등록에서 옵션을 함께 선택하고 코드·이름은 비워 두면 자동 생성.
- 옵션 코드 필수화는 값 등록 API의 깨지는 변경이다.
