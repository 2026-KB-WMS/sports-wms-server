# ADR-021: 창고·지점 코드는 주소의 시·도로 서버가 자동 발급하고, 시·도가 바뀌면 재발급한다

- 상태: Accepted
- 날짜: 2026-10-12

## 컨텍스트
창고·지점 코드를 등록 요청에서 사람이 직접 입력해 형식이 제각각이다. 코드를 일정한 형식으로 통일하고, 주소(시·도)와 거점 종류가 코드에서 드러나게 하고 싶다. 코드는 등록 후 수정할 수 없었는데, 주소를 다른 시·도로 옮기면 코드가 실제 위치와 어긋난다.

## 결정
- **형식**: `{종류}-{시·도}-{일련번호}`. 종류는 창고 `WH`, 지점 `ST`. 시·도는 영문 2자(서울 `SU`, 부산 `BS`, 경기 `GG` 등 17개). 일련번호는 3자리(`001`)이며 1000 이상이면 자릿수가 늘어난다. 예: `WH-SU-001`, `ST-BS-002`.
- **시·도 판별**: 주소의 첫 단어를 시·도 정식명 또는 약칭(`서울`/`서울특별시`, `경기`/`경기도`, `전북`/`전북특별자치도` 등)과 맞춘다. 맞는 것이 없으면 400 `VALIDATION_ERROR`. 주소는 이미 필수 필드다.
- **자동 발급**: 등록 요청은 `warehouseCode`, `storeCode`를 받지 않고 응답으로만 준다. 요청에 보내도 무시한다.
- **채번**: 종류+시·도별로 마지막 발급 번호를 `location_code_sequence`에 저장하고, 그 행을 비관적 락으로 잠가 올린다. 번호는 한 번 쓰면 다시 쓰지 않는다. 과거에 직접 입력된 코드와 겹치면 다음 번호로 넘어간다.
- **재발급**: 발급 형식의 코드를 가진 거점의 주소가 **다른 시·도**로 바뀌면 새 시·도의 다음 번호로 코드를 다시 발급하고 수정 응답에 담는다. 같은 시·도 안의 주소 수정은 코드를 유지한다.
- **기존 데이터**: 과거에 직접 입력된 코드는 변환하지 않고, 주소를 바꿔도 재발급하지 않는다(발급 형식이 아니므로 시·도를 읽을 수 없다).
- **수정 API**: 요청에 `warehouseCode`, `storeCode`가 있으면 기존대로 400이다. 코드를 바꾸는 유일한 경로는 시·도 변경에 따른 재발급이다.

## 근거
- 모든 참조는 `Long xxxId`이고 코드는 표시용 이름표이므로, 재발급해도 재고·입고·출고 데이터는 영향을 받지 않는다.
- 주소를 바꿔도 코드를 그대로 두면 `WH-SU-001`이 부산 창고에 남아 코드가 거짓 정보가 된다. 이전 시 새 거점을 만들어 재고를 옮기게 하는 것보다 재발급이 운영 부담이 작다.
- 개수 + 1 방식(발주 번호)은 코드가 다른 시·도로 빠져나가면 번호가 되돌아가 겹치므로, 별도 채번 행을 쓴다.
- 채번 행은 마이그레이션에서 17개 시·도 × 2종류를 미리 채워 두어 동시 등록 시 행 생성 경합이 없다.

## 검토했던 대안
- 직접 입력을 유지하고 형식만 검증하기: 기각. 번호 충돌과 시·도 표기 오류를 사람이 계속 처리해야 한다.
- 시·도가 바뀌는 주소 수정을 409로 막기: 기각. 거점 이전마다 새로 등록하고 재고를 옮겨야 한다.
- 주소 변경 시 코드를 그대로 두기: 기각. 코드와 실제 위치가 어긋난다.
- 클라이언트가 시·도 코드를 따로 보내기: 기각. 주소와 어긋난 값이 들어올 수 있고, 프론트가 코드 표를 알아야 한다.
- 개수 + 1 채번: 기각. 재발급으로 번호가 겹친다.

## 영향
- 마이그레이션 `V18__create_location_code_sequence.sql`.
- 코드: `common/locationcode`(`RegionCode`, `LocationType`, `LocationCodeIssuer`, 채번 엔티티), 창고·지점 등록·수정 서비스와 요청 DTO.
- 명세: `api/warehouse.md`, `api/store.md`. 공급처·상품 코드는 이번 결정에 포함하지 않는다(직접 입력 유지).
- 프론트: 등록 화면에서 코드 입력란을 없애고, 주소는 시·도로 시작하는 문자열(지도 API의 시·도 포함 주소)을 보낸다. 주소 수정 응답의 코드가 바뀔 수 있다.
