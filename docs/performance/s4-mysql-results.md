# S4 동시성 정합성 MySQL 실행 결과

[`scenario/performance.md`](../scenario/performance.md) S4의 4-1 ~ 4-9를 운영 DB와 같은 MySQL(InnoDB)에서 실행한 결과다. H2 JUnit 테스트로만 확인했던 경합이 MySQL에서도 같은 결과인지 본다(#366).

## 환경과 방법

| 항목 | 값 |
|---|---|
| 실행일 | 2026-11-16 |
| DB | MySQL 8.4 (`docker-compose`의 `wms-db`), 격리 수준은 기본값 REPEATABLE READ, 실험용 DB(`wms_s4`, `wms_s4_before`)를 따로 만들어 개발 데이터와 분리 |
| 앱 | `java -jar`를 호스트에서 직접 실행(JDK 21), 커넥션 풀 기본값(HikariCP 10), 로컬 Windows 개발 PC |
| 요청 도구 | `scripts/perf/s4_concurrency.py` (파이썬 스레드로 같은 순간에 요청). k6는 쓰지 않았다 |
| 데이터 | 마스터 데이터(창고·구역·지점·공급처·SKU)만 시드, 시나리오마다 새 재고·발주를 API로 생성 |
| 수정 후 | `develop` 2026-11-16 (#357, #360, #363 반영) |
| 수정 전 | 커밋 `00af553` (#353 머지 시점, 아직 수정 전) |

- 데드락 건수는 `information_schema.INNODB_METRICS`의 `lock_deadlocks` 증가분이다.
- 로컬 PC 한 대에서 클라이언트와 서버가 함께 돌아 응답시간은 판정에 쓰지 않는다. 이번 범위는 정합성이다.
- 4-6과 4-10~4-12는 이 문서를 처음 쓴 뒤 #367 작업 중에 추가로 실행했다(아래 "추가 실행").

## 새로 발견: 4-1 데드락 (MySQL에서만 발생)

H2 JUnit(`OutboundConcurrencyTest`)은 통과하지만 MySQL에서는 서로 다른 발주가 같은 재고 행에 동시에 할당할 때 데드락이 난다. 이슈 #367로 분리했다.

- InnoDB 데드락 로그: 두 트랜잭션이 같은 `inventory_lot` 행에 S 잠금을 쥔 채 서로 X 잠금(`select ... for update`)을 기다린다.
- S 잠금의 출처는 `stock_allocation` INSERT의 외래 키(`fk_stock_allocation_inventory_lot`) 검사다. `StockAllocationService.allocate`가 할당 행을 먼저 저장하고(`saveAll`) 그 뒤에 재고 행을 잠근다(`outboundStockPort.allocate`).
- 자식 행을 넣기 전에 부모 행(재고)을 먼저 잠그면 해소될 가능성이 크다. 다만 FEFO 배치 계산이 잠금 전 가용 수량을 읽으므로 그 부분의 정합성을 같이 봐야 한다.
- 데드락이 `409 CONFLICT`로 응답돼 사용자는 재시도해도 되는 오류인지 알기 어렵다.

### 추가 실행: 아직 안 돌려 본 경합 (4-6, 4-10~4-12)

같은 환경에서 새 DB로 전체 12개를 한 번 돌렸다. 12건 모두 통과했고 데드락은 0건이다.

| # | 경합 | 응답 | 판정 |
|---|---|---|---|
| 4-6 | 두 SKU(각 2개 로트)를 서로 다른 순서로 요청하는 발주 20건 동시 할당 | 201 20건 | 통과 (할당 합계 100 / 100) |
| 4-10 | 입고 완료(새 재고 행 생성) vs 같은 로트 격리, 100라운드 | 200 199건, 409 `LOT_NOT_AVAILABLE` 1건 | 통과 (5xx·데드락 0) |
| 4-11 | 할당·출고 생성된 발주의 본사 취소 vs 출고 피킹 시작, 20라운드 | 취소 19건 성공 + 피킹 시작 1건 성공, 나머지는 409(`ORDER_IN_PICKING` 등) | 통과 (재고 할당 1 = 취소되지 않은 발주 1건) |
| 4-12 | 같은 출고의 배송 시작 10건, 이어서 배송 완료 10건 | 각각 200 1건, 409 9건 | 통과 |

- 4-10은 코드를 읽고 세운 가설(입고 반영이 새 재고 행을 넣을 때 로트 행에 거는 외래 키 공유 잠금과, 로트 상태 변경이 로트 행 → 재고 행 순서로 거는 잠금의 순환)을 확인하려 했다. 100라운드(요청 200건)에서 재현되지 않았다. 두 요청이 항상 정확히 겹친 것은 아니라(대부분 입고 완료가 먼저 끝났다) 없다고 단정하지는 않는다.
- 4-6은 위 가설과 별개로, 재고 행을 ID 오름차순으로 잠그는 규칙([ADR-006](../adr/006-inventory-pessimistic-lock.md))이 서로 다른 순서의 요청에서도 지켜진다는 것을 확인한다.

### 수정 결과 (#367)

`StockAllocationService.allocate`에서 재고 행 잠금(`outboundStockPort.allocate`)을 할당 행 저장(`saveAll`)보다 먼저 하도록 순서를 바꿨다. 같은 환경에서 전체를 3번 반복했다(24건).

| 4-1 | 수정 전 | 수정 후 |
|---|---|---|
| 응답 | 201 3~4건, 409 `CONFLICT` 16~17건 | 201 10건, 409 `INSUFFICIENT_STOCK` 10건 (3회 모두) |
| 데드락 | 16~17건 | 0건 |

나머지 시나리오(4-2~4-5, 4-7~4-9)는 수정 후에도 전부 통과했다. 재고가 부족할 때의 거절은 잠금 뒤 `InventoryLot.allocate`의 가용 수량 확인이 맡으므로 응답 코드가 의도한 `INSUFFICIENT_STOCK`으로 돌아온다.

## 부수 관찰

- 4-9 수정 전 실행에서 입고 번호 중복(`DUPLICATE_INBOUND_NO`, 409)이 80건 나왔다. 입고 등록을 동시에 요청하면 번호 채번이 겹치고 유니크 제약이 막는 것이다. 정합성은 지켜지지만 사용자에게는 실패다. 수정 후 실행에서는 입고 등록이 먼저 거절돼 나타나지 않았다.
- 4-5는 취소 요청이 점주 권한인데 승인된 뒤에는 403으로 거절돼, 승인·반려·취소 세 가지가 모두 경쟁하지는 못했다. 최종 상태는 항상 하나였다.

```
python scripts/perf/s4_concurrency.py --base-url http://localhost:8081 --label after
python scripts/perf/s4_concurrency.py --only 4-1,4-9 --rounds 20
```
