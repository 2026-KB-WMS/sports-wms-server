# 성능 테스트 시나리오

Notion "비기능 요구사항 명세"(성능 목표 제안, 2026-10-27)와 "비기능 요구사항 정의서"의 수치 기준을 이 서버의 API로 검증하는 계획이다. 기능 흐름 검증은 [`e2e.md`](e2e.md)가 맡고, 이 문서는 **응답시간·처리량·동시성 정합성·내구**만 다룬다.

- **상태**: 계획 단계. 실행 스크립트와 측정 결과는 아직 없다.
- **기준 수치는 확정 SLA가 아니다.** Notion 명세의 "성능 목표 (제안)"이며, 규모 가정이 바뀌면 이 문서의 목표값도 바꾼다.
- 도구는 k6를 쓴다(Notion 검수 조건: JMeter, k6 등). 스크립트는 `scripts/perf/`에 둔다(예정).

## 1. 검증 대상과 제외 대상

Notion 요구사항 중 이 서버에 대응하는 기능이 있는 것만 시나리오로 만든다.

| Notion 요구 | 이 서버의 대응 | 시나리오 |
|---|---|---|
| 단건 조회 P95 1s / P99 2s | `GET /inventory/{id}`, `/orders/{id}`, `/allocations/{id}` 등 | S1 |
| 목록 조회 P95 2s / P99 3s | `GET /inventory`, `/inventory/by-lot`, `/inventory/transactions`, `/orders`, `/outbounds` 등 | S2 |
| 등록/수정 P95 1.5s / P99 3s | 입고 완료, 재고 조정, 할당, 출고 생성 | S3 |
| 동시성 정합성 (음수 재고·이중 할당·중복 처리 0건) | 비관적 락 ([ADR-006](../adr/006-inventory-pessimistic-lock.md)) | S4 |
| 동시 400명, 재고 트랜잭션 300 TPS, 오류율 0.1% 미만 | 혼합 부하 | S5 |
| 72시간 내구 | 평시 부하 | S6 |
| 피크 150% 스트레스 | 장애 지점 확인 | S7 |
| 3년치 데이터에서도 동일 성능 | 이력·재고 대량 적재 | S8 (전 시나리오에 적용) |
| 대시보드 집계 | `GET /dashboard/hq/*`, `/dashboard/warehouse/summary` | S9 |

**측정 불가(대응 기능 없음)**: 바코드 스캔 트랜잭션 0.5s, 웨이브 1만 건 3분, 대량 업로드 1만 건 1분, 외부 연계(OMS/ERP/택배사), 일·월 마감 배치, 비동기 엑셀 다운로드, 오프라인 큐잉, 화면 로딩, 무중단 배포·이중화·RTO/RPO. 해당 기능이 생길 때 시나리오를 추가한다.

## 2. 측정 방식과 Notion 기준과의 차이

- Notion은 단말 E2E 기준이지만 여기서는 **k6가 측정한 HTTP 응답시간**(`http_req_duration`)을 쓴다. 네트워크·단말 시간은 빠지므로 통과해도 단말 기준 통과를 보장하지 않는다.
- 판정은 평균이 아니라 **P95, P99**다.
- 목록 조회의 "페이징 50건 기준"은 적용할 수 없다. 페이지네이션이 보류 중이라([ADR-032](../adr/032-pagination-and-sorting.md)) 목록 API는 전체 건을 반환한다. 이 상태로 측정하고 **응답 건수·바이트 크기**를 같이 기록한다. 페이지네이션이 도입되면 S2를 `size=50`으로 다시 측정한다.
- 인증: JWT 만료가 1시간이고 요청마다 사용자를 다시 조회한다([ADR-016](../adr/016-reload-user-per-request.md)). VU별로 로그인해 토큰을 쓰고, 내구 시나리오는 50분마다 재로그인한다.
- 테스트 환경 사양(CPU·메모리·DB 사양)과 운영 대비 비율을 결과에 반드시 적는다.

## 3. 테스트 데이터

규모 가정(Notion): 창고 3, SKU 20만, 이력 연 1억 건·3년 보관, 동시 접속 평시 200/피크 400.

| 단계 | SKU | 재고 이력(`InventoryTransaction`) | 용도 |
|---|---|---|---|
| 소규모 | 1천 | 1만 | 스크립트 점검, 기준선(빈 DB에 가까운 상태) |
| 중규모 | 5만 | 1천만 | 튜닝 중 반복 측정 |
| 목표 규모 | 20만 | 3억 | 검수 기준 측정 (Notion: 운영 규모로 테스트) |

- 같은 시나리오를 소규모와 목표 규모에서 모두 돌려 **규모에 따른 열화율**을 비교한다.
- 창고 3개, 구역·지점·사용자는 e2e 시드와 같은 구조로 만들고, 부하용 사용자(창고 관리자·점주 각 수십 명)를 별도로 가입·승인한다.
**하이브리드 방식**: TPC-DS는 현실적인 SKU 마스터와 수요 편중만 제공하고, 나머지는 직접 만든 생성기로 합성한다.

| 데이터 | 출처 | 매핑 |
|---|---|---|
| 브랜드·카테고리·상품·SKU | TPC-DS `item` (SF100, 약 20만 건) | `i_brand`·`i_category`·`i_class` → 브랜드·카테고리·상품, 품목 → SKU. 단가는 `i_wholesale_cost`·`i_current_price` 참고 |
| SKU별 수요 비중 | TPC-DS `store_sales` 판매 빈도 | 지점 발주·출고 라인의 SKU 선택 확률(편중). 판매 건 자체는 가져오지 않음 |
| 창고·지점 | 직접 생성 | 창고 3, 지점 수십 개. TPC-DS `warehouse`·`store`는 쓰지 않음 |
| 구역·로트·공급처·창고 발주·입고·검수 | 직접 합성 | e2e 시드와 같은 구조 |
| 재고 이력(`InventoryTransaction`)·상태 이력 | 직접 합성 | 위 수요 편중을 따라 입고·할당·출고·조정을 시간순으로 생성, 이력 합계와 현재 재고가 일치하도록 만듦 |

- TPC-DS `inventory`(주 단위 스냅샷)는 이력이 아니므로 쓰지 않는다.
- 변환·생성 스크립트는 `scripts/perf/`에 둔다(예정). `dsdgen`으로 `item`·`store_sales`만 생성한다.
- 적재는 SQL 대량 적재가 필요하다. 프로젝트의 "DB 직접 INSERT 금지" 규칙의 예외가 되므로 §9 1번 결정 전에는 실행하지 않는다.
- TPC-DS 도구는 TPC 이용 약관이 있어, 생성 데이터를 레포에 커밋하지 않고 스크립트만 커밋한다.

## 5. 시나리오

### S1. 단건 조회

- **대상**: `GET /inventory/{inventoryId}`, `/lots/{lotId}`, `/orders/{orderId}`, `/orders/{orderId}/details`, `/allocations/{allocationId}`, `/outbounds/{outboundId}/details`, `/inbounds/{inboundId}/details`
- **부하**: 100 VU, 5분 유지, 대상 ID는 시드에서 무작위 선택(캐시 효과 방지를 위해 ID 범위를 넓게).
- **판정**: 단건 조회 기준. `/details`는 상태 이력을 포함하므로 별도 집계해 비교한다.

### S2. 목록 조회

- **대상**: `GET /inventory`, `/inventory/by-section`, `/inventory/by-lot`, `/inventory/low-stock`, `/inventory/transactions`, `/orders`, `/outbounds`, `/allocations`, `/inbounds`, `/purchase-orders`, `/products/skus`
- **부하**: 대상별 50 VU, 5분 유지. 필터가 있는 호출(창고·SKU·상태)과 없는 호출을 모두 측정한다.
- **중점**: `/inventory/transactions`는 연 1억 건 증가가 예상되는 테이블이라 목표 규모에서 가장 먼저 기준을 넘길 가능성이 높다. 결과가 기준을 넘으면 어느 쿼리인지 `EXPLAIN`을 첨부한다.
- **판정**: 목록 조회 기준 + 응답 건수·바이트 기록(§2).

### S3. 등록/수정 (재고를 바꾸는 업무 흐름)

단일 사용자 흐름을 반복 실행해 단계별 응답시간을 잰다. 수량 검증은 e2e 시나리오 A·B와 같은 방식이다.

| 흐름 | 호출 순서 |
|---|---|
| 입고 | `POST /purchase-orders` → `PATCH .../confirm`(본사) → `POST /inbounds` → `PATCH .../inspect` → `PATCH .../complete` |
| 출고 | `POST /orders`(점주) → `PATCH .../approve`·`POST /orders/assign`(본사) → `POST /allocations` → `POST /outbounds` → `picking/start` → `picking/complete` → `ship` → `deliver` |
| 재고 조정 | `POST /inventory/adjustments` (조정마다 `beforeQuantity`를 최신으로 조회해 전달) |

- **부하**: 흐름별 20 VU, 10분. 각 VU는 자기 SKU·로트를 쓴다(경합 없는 기준선).
- **판정**: 쓰기 호출(POST/PATCH) 각각이 등록/수정 기준을 충족하는지. 입고 `inspect`·`complete`와 `POST /allocations`는 라인 수에 따라 달라지므로 라인 1·10·50개 케이스를 따로 잰다.

### S4. 동시성 정합성

한 건의 자원에 요청을 몰아 정합성이 지켜지는지 확인한다. **응답시간보다 종료 후 DB 검증이 합격 기준이다.**

| # | 경합 | 동시 요청 | 종료 후 기대 |
|---|---|---|---|
| 4-1 | 같은 로트·SKU에 대해 서로 다른 발주의 `POST /allocations` | 가용 100에 발주 20건 × 수량 10 | 할당 합계 ≤ 100, 가용 음수 0, 초과분은 부족 처리 또는 409 `INSUFFICIENT_STOCK` |
| 4-2 | 같은 발주의 `POST /allocations` 동시 호출 | 20 | 성공 1건, 나머지 409 `ALREADY_ALLOCATED`, 할당 행 중복 0 |
| 4-3 | 같은 입고의 `PATCH .../complete` 동시 호출 | 20 | 성공 1건, 나머지 409, 재고 이중 반영 0 |
| 4-4 | 같은 재고의 `POST /inventory/adjustments`(같은 `beforeQuantity`) | 20 | 성공 1건, 나머지 409 `STALE_QUANTITY` |
| 4-5 | 같은 발주에 승인·취소·보류 동시 요청 | 각 5 | 최종 상태가 상태 전이도에서 허용된 하나, 상태 이력이 전이 순서와 일치 |
| 4-6 | 같은 구역에 입고 적치와 출고 피킹 혼합, 여러 로트를 한 번에 잠그는 요청 교차 | 50 | 데드락·락 타임아웃 건수 기록, ID 오름차순 잠금([ADR-006](../adr/006-inventory-pessimistic-lock.md)) 위반 시 데드락 발생 |

종료 후 검증 쿼리(예시):

- `inventory.quantity < 0` 또는 `allocated_quantity > quantity`인 행 수 = 0
- SKU별 `SUM(allocated_quantity)` = 활성 할당 행의 수량 합
- `InventoryTransaction`의 수량 증감 합 = 현재 재고 수량(시드 기준 대비)
- `StatusHistory`에 같은 전이가 중복 기록된 건수 = 0

알려진 한계: 로트 상태 변경·구역 수용량 검사와의 경합은 [`api/inventory.md`](../api/inventory.md), [`domain/outbound.md`](../domain/outbound.md) 결정·미결 2번에 이미 기록돼 있다. 이 시나리오에서 재현되면 임의로 고치지 말고 그 문서에 결과를 추가해 보고한다. "발주·출고 행을 포함한 전역 락 순서와 할당·해제의 구역 잠금"은 Notion에서 성능 개선 때 확정하기로 한 보류 항목이라 S4-6 결과가 그 근거가 된다.

### S5. 피크 혼합 부하

- **부하 모델**: 램프업 5분 → 400 VU 30분 유지 → 램프다운 5분.
- **업무 비율(초안)**: 단건 조회 40%, 목록 조회 25%, 재고를 바꾸는 쓰기(S3 흐름) 30%, 대시보드 5%. 비율은 실제 사용 패턴이 없어 가정이다.
- **판정**: 전 항목 P95 기준 충족, 오류율 0.1% 미만, 재고 트랜잭션(할당·입고 완료·피킹 완료·조정 등 재고 수량을 바꾸는 호출) 합계 300 TPS 이상, 종료 후 S4 검증 쿼리 통과.
- 평시(200 VU)도 같은 모델로 한 번 측정해 평시/피크 차이를 기록한다.

### S6. 내구

- **부하**: 평시(200 VU, S5 비율) 72시간 연속.
- **관찰**: JVM 힙·GC, DB 커넥션 풀 사용률, 응답시간 P95 추이(시작 1시간 대비 마지막 1시간). 메모리 증가 추세와 응답시간 열화 여부가 판정 대상이다.
- 토큰 만료(1시간)로 인한 401이 오류율에 섞이지 않도록 재로그인을 구현한다.

### S7. 스트레스

- **부하**: 피크의 150%(600 VU)까지 단계 상승(100 VU씩, 단계당 5분), 이후 부하를 낮춰 회복 확인.
- **기록**: 오류율이 0.1%를 넘는 시점, P95가 기준을 넘는 시점, 병목 자원(CPU·DB 커넥션 풀·락 대기), 부하를 낮춘 뒤 정상 응답으로 돌아오는 시간.
- 합격 기준은 없다. Notion 요구가 "장애 지점과 복구 방식 확인"이므로 결과 보고가 산출물이다.

### S8. 데이터 규모 비교

S1~S3을 소규모·중규모·목표 규모에서 같은 부하로 반복하고 P95를 비교한다. 목표 규모에서만 기준을 넘는 호출은 인덱스·쿼리 개선 후보로 기록한다. 이력 테이블의 파티셔닝·아카이빙 전략(Notion 요구)은 이 결과를 근거로 별도 ADR에서 결정한다.

### S9. 대시보드 집계

- **대상**: `GET /dashboard/hq/summary`, `/dashboard/hq/trends?months=12`, `/dashboard/warehouse/summary`
- **부하**: 호출당 20 VU, 5분. 목표 규모 데이터에서 측정한다.
- **배경**: 대시보드는 읽기 전용 집계 쿼리이고 월 범위 인덱스(`received_at`, `delivered_at`, `requested_at`)는 "측정할 수 없어서" 보류했다([ADR-033](../adr/033-dashboard-readonly-aggregation.md)). 이 시나리오가 그 측정이다. 기준을 넘으면 V2 이후 마이그레이션으로 인덱스를 추가하고 ADR-033을 개정한다.
- **판정**: 단건 조회 기준(P95 1s)을 우선 적용한다. 대시보드는 Notion에 별도 기준이 없어 이 값을 가정한다.

## 6. 관찰 지표

k6 결과와 함께 같은 시간 구간의 다음을 저장한다.

- DB: 슬로우 쿼리 로그(`long_query_time=1`), `performance_schema`의 락 대기, InnoDB 데드락 로그(`SHOW ENGINE INNODB STATUS`)
- 애플리케이션: HikariCP 커넥션 풀 사용률·대기 스레드, JVM 힙·GC, 컨테이너 CPU·메모리
- 로그: 락 획득 실패·타임아웃 예외 건수(오류율과 별도 집계)

## 7. 실행 순서

1. 소규모 데이터에서 S1~S4를 한 번 돌려 스크립트와 판정 쿼리를 검증한다.
2. 중규모에서 S1~S5를 돌려 병목을 찾고 튜닝한다(인덱스·쿼리·커넥션 풀·락).
3. 목표 규모에서 S1~S5, S8, S9를 검수 기준으로 측정한다.
4. 통과 후 S7, 마지막에 S6(72시간).
5. 결과는 이 문서 하단 "측정 결과"에 날짜·환경·수치로 추가한다.

## 9. 미결 — 사용자 결정 필요

1. **SQL 대량 적재 예외 허용 여부.** 데이터 구성은 §3 하이브리드로 정했다(TPC-DS 마스터 + 합성). 다만 3억 건 이력은 API 호출로 만들 수 없고, 프로젝트 규칙은 "목데이터는 API로, DB 직접 INSERT 금지"이므로 성능 테스트용에 한해 SQL 대량 적재를 허용할지 정해야 한다. 허용 시 ADR로 남긴다.
2. **테스트 환경.** 운영 사양이 정해지지 않았다. 로컬 `docker-compose`로는 목표 규모 측정이 의미 없을 수 있어 별도 환경과 운영 대비 비율이 필요하다.
3. **페이지네이션 도입 전후 중 어느 쪽을 검수 기준으로 할지.** 도입 전이면 S2 목록 기준은 "전체 건 반환"으로 측정한 값이 되어 Notion 기준(50건)과 다르다.
4. **업무 비율.** S5의 단건/목록/쓰기 비율은 가정이다. 실제 사용 패턴이나 우선하는 업무를 알려주면 바꾼다.
